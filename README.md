# AI鸿蒙应用开发

获课：itazs.fun/21597/AI鸿蒙应用开发

AI鸿蒙应用开发最容易走偏的一步，是一上来就想着做一个“全能Agent”。HarmonyOS 7（API 26）将Agent架构作为核心升级方向，小艺被定义为系统级智能体，开发者需要回答的问题从“我的App怎么用AI”变成了“我的App如何被小艺调用”。但官方给出的路径建议极为克制：不要一上来就做Agent，先用意图跑通最小闭环。这三个层级——意图、Skill、端侧Agent——对应完全不同的复杂度与适用场景，选错起点，后面的投入方向就错了。

起点：意图是成本最低的“被调用”方式

意图解决的是“应用被系统直接唤醒执行特定能力”，复杂度最低。开发者在AGC配置意图能力，定义参数与示例语句，在insight_intent.json中声明执行入口，再在ArkTS中实现executeIntent函数处理参数并返回结果。以“订咖啡”为例，用户对小艺说“帮我订一杯拿铁”，系统解析出意图名称与参数，调用应用注册的执行函数，返回订单号与确认信息。这条链路虽然简单，却覆盖了Agent开发的核心模式：用户表达意图，系统调度能力，应用执行并返回结果。对于功能边界清晰、只需要一个系统级入口的应用，意图已经足够，不必为了“Agent”的名头增加不必要的复杂度。

进阶：Skill与端A2A，两条路径的分寸

当意图不足以覆盖跨应用联动或复杂任务时，路径分化为两条。Skill是将能力封装为小艺可调用的标准化单元，通过小艺开放平台完成开发、调测与上架，获得系统级入口的分发。Skill适合“能力单一但需要被多个场景复用”的情况，比如健身Agent中的训练记录、饮食查询等独立能力。

端A2A模式则适合已有成熟端侧Agent的应用。开发者无需重写Agent，只需在APP端增加一层适配：创建AgentExtensionAbility、在module.json5中注册、定义AgentCard描述Agent能力，然后在小艺开放平台完成关联与配置。这种方式的核心价值在于复用端侧算力与系统API，实现低延迟、高隐私的智能交互，同时让小艺成为你Agent的入口。一位开发者的判断值得参考：如果你的应用已经有一个能对话、能执行任务的Agent，端A2A是最短路径；如果还没有，从意图起步比从零构建Agent更务实。

底座：系统AI能力决定体验上限

无论走哪条路径，应用自身的AI能力决定了用户最终体验。HarmonyOS 7开放的系统级AI能力覆盖视觉与语言方向：图像超分让低清素材在端侧完成高清化，文搜图实现本地语义检索，这些能力的共同特征是端侧执行、隐私优先、无需联网。对于需要自定义模型的场景，CANN Kit提供了在NPU上运行轻量化模型的路径。一个务实的判断来自开发者社区：移动端内置本地大模型建议优先选1B以下、量化后的模型，先用CPU跑通再评估NPU性能，不要假设任意模型都能直接上端侧。

AI鸿蒙应用开发的实战逻辑，本质上是把应用从“用户主动打开的孤岛”改造成“系统智能体可调度的服务节点”。意图管住最小闭环，Skill与端A2A管住入口与分发，系统AI能力管住体验底线。新应用从意图起步，已有Agent的应用走端A2A，需要视觉或语音差异化的场景则从系统AI能力切入。选对起点，比堆砌功能更重要。
